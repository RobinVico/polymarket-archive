2026-06-22 出场策略重设计讨论时, 我先给了技术性 plan + 技术性 ExitPlanMode 摘要, 用户连着两次打断: "用人话给我列一下""讲清楚一点"。

**Why:** 用户不是从工程师视角读代码的, 他要先听懂"现在什么问题 → 怎么改 → 你打算怎么做"再拍板。函数名/行号/schema 对他是噪音。

**How to apply:** 策略/计划/复盘类讨论, **先**给大白话三段式(现在的问题 → 怎么改 → 我准备怎么做), 每条尽量拿他自己的真实仓位/数字举例(如 #79 关领空、$16 漏、绕一圈回原点)。技术细节放后面或 plan 文件里标"执行用"。ExitPlanMode/重大动作前先用人话讲一遍, 别直接甩技术摘要。代码注释 / 技术报告 仍按原样写 —— 这条只管"对用户口头解释"的场合。相关: [[event-driven-exit-keep-status-quo]]。

**每次升级 / commit / 上传后, 必须主动汇报"改了什么" (用户 2026-06-22 明确确认这是固定预期)**: 大白话列出 ① 改了什么(+为什么, 拿真实例子) ② 复检发现的问题 + 怎么解决 ③ 改了哪些文件(代码+文档) ④ 安全确认(敏感文件 v4.db/盈亏/research_data 有没有被上传; 推 dev 还是 public) ⑤ 验证结果(重启/页面200/报错)。不要默默改完就完事。
